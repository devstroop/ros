# Gaps from v1

**Status:** Living document.
**Compared:** Eatery v1 (`../eatery`, the Flutter app) against Restaurant OS
(`apps/ros`, the Zig app on the Native SDK).
**Method:** read from both trees. v1 file paths are relative to
`../eatery/`; Restaurant OS file paths are relative to this repository's root.

This page has three parts, and they are deliberately kept apart:

1. **What Restaurant OS drops or defers**, and what the restaurant loses by it.
2. **What Restaurant OS fixes** that v1 got wrong.
3. **What Restaurant OS still owes v1** — features v1 had that Restaurant OS has not rebuilt yet,
   with the phase that owes them.

A feature that Restaurant OS dropped entirely is in part 1 and not in part 3. A
feature that Restaurant OS dropped *for now* is in part 1 with a deferral phase and
also in part 3.

---

## 1. What Restaurant OS deliberately drops or defers

| Feature | v1 | Restaurant OS | Why | What the restaurant loses |
|---|---|---|---|---|
| **Multi-company** | `company` table with `nextInvoiceNo`, `invoicePrefix`, `subscriptionId`, `adminEmployeeId`, and a `companyId` foreign key on `orders` plus 19 more tables (issue #129 in `../eatery/ISSUES.md`) | One company per database. `apps/ros/src/schema/0001_core.sql` declares `company` with no company scoping anywhere else | The multi-company story was never used by a real deployment and it put a tenant filter on every query, every repository and every screen. Restaurant OS's `company` row exists to hold the name, the currency and the tax mode — not to be a tenant boundary | An operator who ran two kitchens from one database in v1 cannot do that in Restaurant OS. Two kitchens means two databases, and there is no screen that switches between them |
| **Google Drive backup** | `../eatery/lib/services/cloud/google_drive.dart`, with `googleapis` and a user-consent OAuth flow | No cloud backup. `fx.fetch` plus `fx.credentials` would allow a manual upload, but nothing is built | A cloud backup is a hosted service with an account system, an OAuth app and a data-egress story. Restaurant OS's release scope is a LAN product with no cloud dependency (see `../eatery/README.md`: "no cloud dependency") | A restaurant that used Drive to move a database between machines loses that path. The replacement is a file copy of the database, which `data_management` has to document — that is a Phase 6 deliverable, not something that exists |
| **Lottie animations** | `../eatery/assets/lottie/brand.json`, `hurray.json`, `1699657402574.json`, used in `../eatery/lib/pages/display/display_page.dart`, `../eatery/lib/pages/create_company/result.create_company.dart` and `../eatery/lib/components/eatery_core_widgets/app_order_card.dart` | Dropped. The SDK has no animation runtime and no custom-paint hook | The `lottie` package is a Flutter plugin with a Dart runtime; the Native SDK's markup grammar has no tween, no sprite sheet and no per-frame hook. The one thing Lottie was doing on the customer display — a celebration when an order was ready — has a text equivalent | The customer display no longer celebrates. A customer's order appears as a changed label rather than an animation, and the brand moment is gone. The elapsed-time text on the display board is kept |
| **Excel / XLSX import and export** | `../eatery/lib/pages/dashboard/data/data_management.page.dart` reads with `Excel.decodeBytes` and writes with `Excel.createExcel`, producing `EXPORT-<timestamp>.xlsx`; the `import` and `export` routes are in the router | Deferred to CSV. `docs/decisions/0012-csv-first-interchange.md` records the decision | The SDK has no spreadsheet reader or writer, and a spreadsheet is a zip container with a shared-string table and a style sheet — a library, not a feature | An owner who sent a spreadsheet to their accountant cannot any more. CSV covers the same data and opens in a spreadsheet, but loses cell formatting, multiple sheets and formula columns. The CSV importer and exporter do not exist yet — Phase 2 |
| **Image picker and the image library** | `../eatery/lib/pages/dashboard/utility/image_library.page.dart` uses `image_picker` for the gallery and the camera, plus a file picker; `product.image_path` and `company.logo` carry the results | Deferred. `product.image_path` and `company.logo` exist as columns in Restaurant OS's schema, but there is no picker | The SDK has no native file-open panel and no camera access (`docs/architecture/11-capability-gaps.md` lists both as gaps). A sidecar is one option; a known-directory browser is another | Menu items cannot carry a photograph in Restaurant OS today. The v1 product page had an image, and the customer-facing display is where that image would have been shown. The kitchen does not care; the customer does |
| **BLE printing from inside the app** | `../eatery/lib/support/bluetooth_thermal_printer/` — a vendored Bluetooth thermal printer stack with an ESC/POS generator, used by `../eatery/lib/services/printing/print_invoice.dart` via `BluetoothPrinterService`; `printer.bluetoothAddress` and `printer.type = bluetooth` in the schema | The app never talks to a printer. `apps/ros/src/schema/0009_printing.sql` stores the printer configuration and `tools/print-sidecar/` is meant to own the device | The SDK has no Bluetooth stack and no ESC/POS. The sidecar keeps a network stack out of the pure core, at the cost of a second program to build, sign and ship | Nothing yet — Restaurant OS cannot print at all until Phase 5. The loss is delayed, not permanent: the restaurant does not lose receipts, it loses them *later*, and the phase that owes them is Phase 5 |
| **WebSocket sync inside the app** | `../eatery/packages/eatery_core/lib/data/sync/sync_server.dart` and `sync_client.dart`, with eight message types in `sync_message.dart`, mDNS on `_ros-sync._tcp:9876`, and host election by uptime | The app never speaks a network protocol. `apps/ros/src/schema/0010_sync.sql` holds `op_log`, `device` and `sync_state`; `tools/sync-sidecar/` is meant to own the socket and the election | The SDK has no WebSocket and no mDNS, and `fx.fetch` rejects non-HTTP(S). The protocol was already table-shaped, so the protocol moves to a sidecar and the app keeps writing rows | Nothing yet — Restaurant OS cannot sync at all until Phase 4. When it does, the topology is the same: a host, leaves, LWW on the logical clock |
| **Pie charts** | `../eatery/lib/pages/dashboard/components/dashboard_charts.dart` draws a `_PaymentPieChart` with `fl_chart`, alongside a revenue line chart and an order-volume bar chart | No pie chart. The SDK has no pie series kind; a bar or a stacked bar is the substitute | `fl_chart` is a Flutter package, and the SDK's chart element has no pie kind. The payment split is also available as numbers, which is what a report needs | The dashboard's payment-mix view changes shape. The information survives — a bar chart or a table carries the same split — but the round pie is gone |
| **Printable reports** | `../eatery/lib/services/printing/print_report.dart` — `PrintReport.printReceipt` takes a list of orders, an account and a `from`/`till` range, and `generateReceipt` produces the bytes | Deferred to Phase 5, alongside the receipt itself. `compliance_report` in `apps/ros/src/schema/0008_compliance.sql` holds the X/Z snapshot, so the data exists | A report that prints is a report layout, and the layouts belong with the ESC/POS encoder in the print sidecar rather than in the app | No printed X or Z report until Phase 5. The on-screen report in `reports` is Phase 2 |
| **Subscription and the upgrade page** | `../eatery/lib/pages/activation/upgrade.page.dart` shows plans and asks the user to "Contact us to get subscription"; `subscription` is a table in the schema | The `subscription` table exists in `apps/ros/src/schema/0008_compliance.sql` and the `upgrade` screen exists in the enum, but nothing is built | Restaurant OS is free and open source. A subscription screen is a sales surface for something that is not sold | Nothing is lost for the restaurant. What is lost is the author's ability to show a paid tier — if that is ever wanted, it is a separate product decision, not a port |
| **Loyalty as a user-facing feature** | `../eatery/packages/eatery_core/lib/data/repositories/loyalty_repository.dart` with `getByCustomer`, `recordVisit` and `redeemPoints`, the `customer_loyalty` and `loyalty_transaction` tables, and points shown on `../eatery/lib/pages/dashboard/customer/view.customer.page.dart` | The three tables exist in `apps/ros/src/schema/0004_customers.sql`; no screen shows points and no repository reads them | The tables are cheap to keep and the ledger is the hard part. The rule is: the data model survives, the feature does not ship until a customer screen can show it | A regular cannot see their points and the cashier cannot redeem them. A restaurant running a loyalty scheme loses the scheme's front end, not its history — the ledger rows are still there if it is rebuilt |
| **The employee time clock UI** | `../eatery/packages/eatery_core/lib/data/repositories/shift_repository.dart` has `saveShift`, `deleteShift`, `clockIn` and `clockOut`, and `assets/db/schema.sql` declares `shift` and `time_entry`. **There is no screen**: the only reference in `lib/` is the debug tool `../eatery/lib/dev/database_inspector.dart` | `shift` and `time_entry` exist in `apps/ros/src/schema/0007_ops.sql`. No repository, no screen | The tables are needed by the X/Z report and the shift reconciliation, which are compliance requirements. The clock-in screen is a separate piece of work that v1 never had either | Nothing is lost, because v1 never had it. The honest statement is that v1 had the data model and the repository and stopped there, and Restaurant OS currently has the tables and not even that. The clock-in screen is owed by Phase 2 alongside the shift and the X/Z report |

### What is not a gap

| Item | Note |
|---|---|
| The Flutter widget ecosystem | Not a feature. Its loss is the point of the rewrite, and it is accounted for in the rows above |
| Mobile packaging | v1 shipped Android, iOS, macOS, Windows and Linux. Restaurant OS's `apps/ros/app.json` lists macOS, Linux and Windows. A restaurant POS on a tablet is a real use, and it is deferred, not cancelled |
| The `fl_chart` line and bar charts | The SDK has line, area and bar chart kinds. Only the pie is lost |
| The `lottie` celebration on the order card | The order card still shows status; only the animation is gone |

## 2. What Restaurant OS fixes that v1 got wrong

| v1 | Evidence in v1 | Restaurant OS | Evidence in Restaurant OS |
|---|---|---|---|
| **Money as a float** | `../eatery/assets/db/schema.sql`: `subTotal REAL NOT NULL`, `discountTotal REAL NOT NULL`, `taxTotal REAL NOT NULL`, `grandTotal REAL NOT NULL`, `roundOff REAL NOT NULL` on `orders`; `amount REAL NOT NULL` on `payment`; `rate REAL NOT NULL` on `tax_slab` | Money is `INTEGER` minor units and rates are integer basis points. A day's total can be reconstructed exactly from the stored integers | `apps/ros/src/schema/0001_core.sql`..`0010_*.sql`: `price_minor`, `total_minor`, `rate_bps` with `CHECK (rate_bps BETWEEN 0 AND 10000)`; `apps/ros/src/domain/models.zig` `price_minor: i64`; `apps/ros/src/tests.zig` has the test "money stays integer: two hundred and fifty cents is never a float" |
| **Plaintext PINs** | `../eatery/assets/db/schema.sql`: `employee.pin TEXT` — the PIN in the clear. The audit lists defect **A9** (one PIN for the whole restaurant, held in `company.password`) and **A7** (no complexity rules) | A salted SHA-256 digest. The plaintext never reaches the disk, and the salt is per installation, so two restaurants with the same PIN do not share a digest | `apps/ros/src/schema/0001_core.sql` `employee.pin_hash TEXT`; `apps/ros/src/data/auth.zig` `hashPin` and `makeSalt`; `apps/ros/src/core/update.zig` hashes before the query and the SQL compares the digest |
| **The router-based RBAC** | `../eatery/docs/architecture/routing.md` puts the role check in a GoRouter `redirect:` callback, and the same document records that permission-based routing was "not yet implemented" while about 81 `Navigator.push` call sites bypassed the router. The audit lists defect **A8** | One pure function, `rbac.allows(role, screen)`, consulted before any state change, walked over every `(role, screen)` pair by a test | `apps/ros/src/core/rbac.zig`; `apps/ros/src/core/update.zig` `go()` refuses before it pushes; `apps/ros/src/tests.zig` "the permission matrix is total: every role against every screen" |
| **A second SQLite engine vendored into the app** | `../eatery/libeaterystore/` is a Zig C library bound through `dart:ffi`; `../eatery/docs/plan/issue-inventory.md` defect **L1**: `static EateryStore? _store` in `order.function.dart` — a global mutable handle. Defect **R1**: blocking FFI reads mixed with `Future`-wrapped writes. Defect **R2**: every `getAll*()` ran `SELECT *` with no limit | One engine-owned store. Migrations are applied by the platform before the first frame. The app never opens a connection and never issues a `PRAGMA` | `apps/ros/app.json` declares the `sqlite` capability; `apps/ros/src/schema/` plus `migrations.lock.json`; `apps/ros/src/data/repos.zig`; `apps/ros/src/data/page.zig` reads the engine's row format by column name |
| **The missing repositories** | `../eatery/ISSUES.md` issue **#153**: "Add repositories for 8 orphan SQL tables" — tables with rows and no way to read or write them | Every entity has a named SQL constant, a loader and a decoder, or is listed in `docs/plan/backlog.md` with the screen that owes it. The coverage table is public | `apps/ros/src/data/repos.zig`; `docs/architecture/data-model.md` section 4 has the per-entity read/decode/write table; `docs/plan/backlog.md` names the owner of each gap |
| **The stale router regression test** | `../eatery/test/router_regression_test.dart` asserts `expect(routeNames.length, 54, reason: 'Expected 54 named routes')` and checks that 54 names resolve — while `../eatery/lib/core/router/app_router.dart` now declares **77** `GoRoute` entries. The test passes while covering 23 routes not at all, and the duplicated 54-name list at the bottom of the file is a second copy to keep in step | One source of truth for the navigation surface: the `Screen` enum, the permission matrix, and a test that pins the ordinal of every mounted screen | `apps/ros/src/core/navigation.zig`; `apps/ros/src/app.native` gates on literal ordinals; the ordinal test is a Phase 1 deliverable in `docs/plan/roadmap.md` |
| **The hardcoded OAuth secret** | `../eatery/lib/services/cloud/google_drive.dart` line 8: `const _clientSecret = "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";` — a live Google client secret in the source tree. `../eatery/ISSUES.md` issue **#89**, priority P0, still open | No OAuth client and no cloud service in Restaurant OS at all, so there is no secret to leak. A future manual backup would use the OS keychain through `fx.credentials` and a secret the user supplies | The SDK's `credentials` capability is declared in `apps/ros/app.json`; `docs/plan/gaps-from-v1.md` section 1 records the cloud backup as dropped |
| **The silent catch blocks** | `../eatery/lib/pages/dashboard/data/data_management.page.dart` has 19 `catch` clauses; the audit records defect **B5** / **N17**: "15 silent catch(e) with only debugPrint". Issue **#122** is titled "Add user-facing error handling — 65 silent catch blocks" and is priority P0 | There is one error channel. `model.error_text` is set on failure and the shell renders it as a dismissible banner, and the database result carries an outcome the `update` arm has to look at | `apps/ros/src/app.native` binds `has_error` and `error_message`; `apps/ros/src/core/update.zig` sets `error_text` on every failure arm and clears it on `dismiss_error`; `apps/ros/src/core/msg.zig` carries `db_failed` |
| **Untestable business logic** | `../eatery/docs/plan/issue-inventory.md` defect **P5**: about 130 lines of `placeOrder()` — order creation, tax calculation, table status update and print logic — inside `cart.page.dart`, a widget. Defect **O8**: `Order.status` is a raw string, so any value can be assigned. Defect **P5**, **P6**, **P8**: cart state held in a provider with no lifecycle management | The business rules are in `update`, which is a pure function of `(model, message)`. The status machine is an explicit enum with an explicit transition function. The tests dispatch messages the way the runtime does and assert on the model | `apps/ros/src/core/update.zig` `nextStatus` and `placeOrder`; `apps/ros/src/domain/models.zig` `OrderStatus`; `apps/ros/src/tests.zig` — 12 tests, including "the cart adds, counts and totals in minor units" and "the permission matrix is total" |
| **No transaction around an order write** | `../eatery/docs/plan/issue-inventory.md` defect **DB5**: `SqliteOrderRepository` saves the order, then writes its line items in a loop, with no transaction. A crash midway leaves orphaned line items | One `dbExec` carries the order and every line, and the engine runs the statements atomically. The same applies to a status change and its history row | `apps/ros/src/data/repos.zig` `saveOrder` and `setOrderStatus` |
| **Mixed time shapes** | `orders.createdAt INTEGER`, `orders.updatedAt INTEGER`, `payment.date INTEGER` alongside formatted strings elsewhere; `../eatery/packages/eatery_core/lib/data/sync/op_log_entry.dart` carries `timestamp` as a logical clock while the rest of the app carries epoch millis | One shape: `INTEGER` epoch milliseconds, UTC, everywhere, with recurring wall-clock values stored as minutes-from-midnight or a calendar date | `apps/ros/src/schema/0001_core.sql`..`0010_*.sql`; `apps/ros/src/domain/models.zig` |
| **Loose type affinity and no enum constraints** | 39 tables in `../eatery/assets/db/schema.sql` with no `STRICT` keyword, so a column declared `INTEGER` accepts the text `'12'` | 46 tables, every one `STRICT`, with `CHECK` constraints on every enum and boolean. `native check` rejects a non-`STRICT` table at build time | `apps/ros/src/schema/`; `docs/architecture/data-model.md` section 3 |
| **Order lines that follow the product price** | `../eatery/assets/db/schema.sql` `order_product` references the product, so a price change rewrites history | `order_line.product_name` and `unit_price_minor` are frozen at the moment of the sale | `apps/ros/src/schema/0005_orders.sql` |
| **A `dynamic`-typed and interface-drifted repository layer** | `../eatery/docs/plan/issue-inventory.md` defects **D1** (nine `as dynamic` casts to reach a method the interface does not declare), **D3** (the `DiningTableRepository` interface is incomplete, so pages cast to the concrete class), **O6** and **CS3** (a `dynamic` row type in a list widget) | One typed row struct per entity in `apps/ros/src/domain/models.zig`, one decoder per dataset, and a decoder that addresses columns by name so a column reorder in SQL cannot swap two fields | `apps/ros/src/data/repos.zig`; `apps/ros/src/data/page.zig` `indexOf` |
| **A single PIN for the whole restaurant** | `../eatery/docs/plan/issue-inventory.md` defect **A9**: `company.password` is the single PIN, so no waiter can be distinguished from another and no chef can be distinguished from a cashier | A PIN per employee, each with a role. The sign-in returns the employee id and the name, so an order records who placed it | `apps/ros/src/schema/0001_core.sql` `employee.pin_hash`; `apps/ros/src/core/update.zig` `login_checked` sets `employee_id` and `employee_name`; `apps/ros/src/schema/0005_orders.sql` `orders.employee_id` |
